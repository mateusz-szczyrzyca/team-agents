Errors — `ERR`\n\n- **ERR-1 Nothing is ignored.** Every fallible outcome is (a) propagated with `?`, with context; or (b) recovered by a fallback that is specified behaviour and has a test; or (c) — only where it cannot be propagated: in `Drop`, or during cleanup while another error is already being returned — logged at `warn` or `error` with context, next to a comment saying why. \"Cannot happen\" and \"does not matter\" are not handling. If carrying on really is right, write the decision down: match the error, log it, comment why.\n- **ERR-2 All of these count as ignoring:**\n  - `let _ = f();`, `_ = f();`, `f().ok();`, an empty or catch-all `Err(_) => {}` arm;\n  - `if let Ok(x) = f()` or `while let Ok(x) = …` with the `Err` case unhandled;\n  - `.ok()`, `.unwrap_or(…)`, `.unwrap_or_default()`, `.unwrap_or_else(|_| …)` used to make a failure disappear rather than as a specified fallback;\n  - `filter_map(Result::ok)`, `.flatten()` or `.flat_map(…)` over `Result`s — failed items vanish; collect into `Result<Vec<_>, _>` or handle each error;\n  - `map_err(|_| …)` — the cause is thrown away;\n  - concurrency: a dropped `JoinHandle` (thread or task), an unchecked `JoinError`, an ignored `send` / `recv` error or timeout;\n  - I/O: `write` for `write_all`, `read` for `read_exact` (byte count ignored); a `BufWriter` dropped without `flush()?`; data that must survive a crash without `sync_all()?`; `Command::status()` / `output()` without checking `ExitStatus::success()`; a child process never waited for;\n  - lossy shortcuts — `as` casts, `from_utf8_lossy`, `to_string_lossy` — unless losing data is the specified behaviour;\n  - a `None` that means failure (lookup miss, `checked_*` overflow, `.parse().ok()`): convert it with `ok_or_else` and propagate;\n  - `mutex.lock().unwrap()`: map poisoning to an error, or recover on purpose with `PoisonError::into_inner` and a comment why the data is still consistent;\n  - unchecked FFI return codes and null pointers;\n  - logging the error and continuing as if the operation had succeeded.\n- **ERR-3 No panic paths in production code** — library or binary: no `unwrap()`, `expect()`, `panic!`, `todo!`, `unimplemented!`, `unreachable!`, and no `assert!` on anything derived from input. A panic means \"bug\", never \"bad input\" or \"I/O failed\". If failure is truly impossible, first make the types say so (§6). Only when they cannot: `expect(\"<the invariant>\")` under a local `#[expect(clippy::expect_used, reason = \"…\")]`. `debug_assert!` and `assert!` may state internal invariants; document them under `# Panics`.\n- **ERR-4 `thiserror` by default.** Every library crate and every module with domain logic returns its own typed error. `anyhow` is allowed only in the top layer of a binary (`main` and the glue that merely reports errors to a human), in tests, examples, benches and build or xtask scripts — never in a library's public API. Never `Box<dyn Error>`, `String`, `&str`, `()`, `bool` or `Option` to signal failure. No other error crates (`eyre`, `snafu`, …) unless the repository already uses them.\n- **ERR-5 Narrow error types.** One enum per module or operation, holding only the failures that can really happen there — not one crate-wide `Error`. A caller can match it exhaustively with no dead arms. Compose upwards with `#[source]` or `#[from]`.\n- **ERR-6 Variants say what failed, in domain terms, with the context needed to act:** path, id, key, offending value (never a secret). Not `Io(#[from] io::Error)` — which file, which operation? Use `#[from]` only where one source type has exactly one meaning; otherwise build the variant in `map_err(|source| …)`.\n- **ERR-7 Keep the cause chain.** Wrap the underlying error as the `source` (`#[source]`, `#[from]`, `#[error(transparent)]`). Never stringify it into a field, never drop it. Do not also print the source in the wrapper's message: reporters walk `source()` and would show it twice.\n- **ERR-8 Error type hygiene.** Messages are lowercase, concise, without a trailing full stop, and name the failed operation and value. Types are `Debug` + `Error` + `Send + Sync + 'static`, small (box large payloads), and `#[non_exhaustive]` when public and likely to grow. No third-party error type in a library's public API unless that dependency is deliberately part of the API.\n- **ERR-9 With `anyhow`:** `.context(…)` or `.with_context(|| …)` on every `?` that crosses a boundary (what was being done, with which input); print the whole chain (`{:#}` or `{:?}`); never `downcast` to decide what to do — an error you branch on needs a type.\n- **ERR-10 Handle each error once.** Return it (with context) or handle and log it — not both.\n- **ERR-11 Binaries** return `ExitCode` or `Result` from `main`: non-zero exit on failure, the full cause chain on stderr. Severity and verdict\n\nEvery finding has exactly one of three severities. Write it in brackets, in capitals, and put nothing else in the\nbracket: the rule ID goes after it (`[MAJOR] ERR-3`), never in it.\n\n- `[BLOCKER]` — the logic does not work as it must, or there is a serious error: a red gate or build, a defect in\n  the code that the task or a test shows, a RED commit that does not build or whose test passes, an existing test\n  changed without the human, a size above 2000. It is fixed in the code and cannot be explained away.\n- `[MAJOR]` — a deviation from a specification (the task, the developer rules, `AGENTS.md`) that comes with no\n  explanation of why.\n- `[MINOR]` — everything else: a real improvement that does not block. At most 10, the most valuable first. The\n  limit applies to `[MINOR]` only.\n\nThe tags of §4 map to them once, here: `B` → `[BLOCKER]`, `M` → `[MAJOR]`, `m` → `[MINOR]`. They are defaults.\nRaise a finding one level only when it causes a concrete defect in this PR, and say which. A deviation the PR\nrecords under *Deviations* with a reason that holds, and that you accept, is not a finding: list it under ACCEPTED\nDEVIATIONS. If you cannot tell whether something is a violation, find out first: read, run. If it stays open and\nwould block, report it as a `[BLOCKER]` that asks for the evidence.\n\n**Verdict:** no `[BLOCKER]` and no `[MAJOR]` → `APPROVE`; otherwise `REQUEST_CHANGES`. `[MINOR]` findings never\nchange the verdict. A report that says `APPROVE` has no `[BLOCKER]` or `[MAJOR]` finding, and one that says\n`REQUEST_CHANGES` has at least one: the harness sends back a report that contradicts itself. If your harness or\ntask prescribes verdict keywords or a report layout, use those and keep the content.\n\n**NEEDS HUMAN** is independent of the verdict. Never `#[allow]`. Never crate- or module-wide. Never `warnings`, `clippy::all` or `clippy::pedantic` wholesale. A lint that fires only under some `cfg` gets a conditional expectation: `#[cfg_attr(<cfg>, expect(…))]`. Every suppression is listed in the PR.\n- **LINT-4** Never edit lint, format, toolchain or CI configuration to get green (`[lints]`, `clippy.toml`, `rustfmt.toml`, `rust-toolchain.toml`, `deny.toml`, workflows). A configuration change is its own PR, and only when the task asks for it.\n- **LINT-5** No `#![deny(warnings)]` in source: it breaks the build on every toolchain update. Strictness lives in the gate.\n- **LINT-6** Stay inside the repository's edition and MSRV (`rust-version`). Stable features only, unless the repository is on nightly.\n- **LINT-7** In a repository without a strict lint setup, follow these rules by hand, check your own change by passing the appendix lints as `-W clippy::<lint>` flags, and propose the baseline from the appendix as a separate PR.\n- **LINT-8 Green means green on the first run.** A check that fails and then passes with nothing changed is flaky, not green. Never hide it by running it again. A failure in a test your change adds or touches, or one your change made flaky, is your bug: fix it (TDD-8). When the gate fails on a test or check your change does not touch and cannot have changed: 1) keep the whole output of that failure — the test's name, the message and the location of its panic — in a file under `build/`; 2) run the gate once more, and only once; 3) if it passes, go on, and list the failure in the PR under `## Flaky checks` with the test, the message and the location; 4) if it fails again in the same place, it is not flaky for this change: find the cause, and ask the human only when the cause is in code your task may not change.\n\n## 5. Test-driven development — `TDD`\n\n- **TDD-1 Red → green → refactor, one behaviour at a time, each step a commit of its own.**\n  1. *Red.* Write one small test for the next behaviour. A compile error is not red: add the thinnest stub the test needs — the signature with a body that returns a wrong value (accept everything, refuse everything, an empty collection). Not `todo!()`: a panic in the stub fails the test for the wrong reason, and `todo!()` is never committed. Run the test and watch it fail **for the right reason**: on its assertion. A new test that passes against the stub has not been red: choose a stub value it rejects. Commit the test and its stub alone: the subject starts with `RED:`, the message ends with the test command and the failing lines. A RED commit builds, and fails only on its new tests.\n  2. *Green.* Write the least code that passes. Nothing the tests do not demand. Commit it with a subject that starts with `GREEN:`. This commit does not touch the tests (TDD-14).\n  3. *Refactor.* Clean up with the tests green and unchanged. Re-run after every step.\n- **TDD-2 No behaviour without a test.** Every new function, branch, error variant and bug fix has a test that fails when that behaviour is removed. Check it: break or revert the new code and see the new tests go red.\n- **TDD-3** A bug fix starts with a failing regression test that reproduces the bug.\n- **TDD-4** Refactoring changes neither behaviour nor tests. Code without coverage gets characterisation tests first.\n- **TDD-5** Test behaviour through the public interface, not implementation details. A refactoring must not break tests.\n- **TDD-6** Cover the happy path, every error variant (triggered through the public API — inject a failing dependency if that is what it takes), the boundaries (empty, zero, one, max, off-by-one, overflow), invalid input, and non-ASCII text wherever text is handled.\n- **TDD-7 Assert precisely.** `assert_eq!` on whole values. Errors by variant and fields (`matches!`, `let … else`), never by comparing `Display` or `Debug` strings, never a bare `assert!(r.is_err())` or `assert!(r.is_ok())`.\n- **TDD-8 Deterministic and isolated.** No real network, wall clock, `sleep`, unseeded randomness, fixed ports, shared global state, environment mutation, dependence on test order, or files outside a `tempfile` directory. Inject the clock, the RNG and the I/O. Async time runs on the runtime's paused clock, not on real sleeps.\n- **TDD-9 Readable.** The name states behaviour and condition (`returns_not_found_when_user_is_missing`). Arrange, act, assert. One reason to fail. Table-driven cases instead of copy-paste.\n- **TDD-10 The right kind of test.** Unit tests in a file of their own beside the code: `#[cfg(test)] mod tests;` in the module, the tests in its `tests.rs` — a change of the tests is then a change of test files, which TDD-14 and the size count (PR-1) can see. An inline `mod tests { }` that is already there stays and may grow; moving it is a mechanical change of its own (PR-6). Integration tests in `tests/`, through the public API only. Doctests for public examples. Property tests for parsers, codecs (round-trip) and invariants. Compile-fail tests (`trybuild`, or a `compile_fail` doctest) for guarantees a type claims to give. Miri for `unsafe`. `loom` for hand-written synchronisation. Use the tools the repository already has.\n- **TDD-11 Existing tests are a contract.** Never delete, `#[ignore]`, comment out or loosen a test to get green. Change an existing test only when the task explicitly changes the behaviour it specifies, and list every modified or removed test with its reason in the PR. No skipped, empty, placeholder or assertion-free tests.\n- **TDD-12** No test-only paths in production code: no `if cfg!(test)`, no flags or wider visibility just for tests. Test helpers live under `#[cfg(test)]` or in `tests/`.\n- **TDD-13** Prefer real implementations and in-memory fakes. Mock only process boundaries (network, clock, OS), behind a trait you own.\n- **TDD-14 A test is frozen once committed.** From its RED commit on, a test of your own change is a contract like an existing one (TDD-11): later commits add tests; they never edit, delete, `#[ignore]` or loosen one. If a committed test is itself wrong — it asks for what the task does not, or no correct implementation can pass it — do not bend the code to it (GEN-4) and do not repair it in passing. Correct it in a commit of its own that touches tests only: the subject starts with `TEST-FIX:`, the body says what was wrong. A change of a test that a review asked for is a `TEST-FIX` too, with the finding as its reason. The harness lists every `TEST-FIX` commit in the PR under *Tests changed after RED* by itself, from the commit's message — you do not edit the pull request for it, so write the reason into the commit; the reviewer accepts or rejects each one. Check it before you hand over: for each RED commit, `git diff <red> HEAD -- <its test files>` shows added lines only, or the lines of a listed `TEST-FIX`.\n\nExempt from test-first: documentation, comments, formatting, pure moves and renames, dependency or configuration changes that alter no behaviour. A change of behaviour that cannot have its test first says so in its commit message: `Test-First: not possible — <reason>`.\n\nIn test code `unwrap`, `expect`, `panic!` and indexing are fine — a panic is a failed test. Shared helpers in `tests/` return `Result`. An example test is in §7.\n\n## 6. Types: make invalid states unrepresentable — `TYP`\n\nFor every invariant, take the highest rung you can reach:\n\n1. **Unrepresentable** — the wrong program does not compile.\n2. **Checked once, at the boundary** — a constructor returns `Result`; from then on the type carries the proof.\n3. **Checked at every use** — returns `Result` each time.\n\nNever: unchecked, assumed, or merely documented.\n\n- **TYP-1 Parse, don't validate.** Turn raw input into a domain type at the boundary (`TryFrom`, `FromStr`, `new` → `Result`). Code behind the boundary takes the domain type and never checks again.\n- **TYP-2 Seal the invariant.** Private fields, and no way around the constructor. That includes derives: no `Default` that yields an invalid value, `Deserialize` only through validation (`#[serde(try_from = \"…\")]`), no `pub` field, setter or `DerefMut` that can break it.\n- **TYP-3 Newtypes for domain values.** Ids, quantities with units, validated strings (`UserId`, `Millimetres`, `Email`) — not bare `u64`, `f64`, `String`. Two arguments of the same primitive type must not be swappable by accident. Use the strong types std already has: `Duration`, `Instant`, `SystemTime`, `Path`/`PathBuf`, `IpAddr`, `SocketAddr`, `NonZero*`.\n- **TYP-4 Enums, not flags, strings or magic values.** No `bool` parameters: use a two-variant enum. No state, kind or mode as a string or integer code. No sentinel values (`-1`, `0`, `\"\"` meaning \"none\"): use `Option` or an enum.\n- **TYP-5 One state, one variant.** A struct with correlated `Option` or `bool` fields becomes an enum whose variants carry exactly the data that is valid in that state.\n- **TYP-6 Exhaustive `match`.** No `_ =>` arm on an enum defined in this workspace: adding a variant must break the build everywhere a decision is needed. Wildcards are for foreign `#[non_exhaustive]` enums and open domains (integers, strings).\n- **TYP-7 Encode protocols in ownership.** One-shot operations take `self` by value. A call order that matters becomes typestate (`Connection<Handshaking>` → `Connection<Ready>`). Paired actions (lock/unlock, begin/commit) are RAII guards, not \"remember to call X\".\n- **TYP-8 Checked numerics.** Integer conversions with `From` / `TryFrom`, never `as` — it truncates and wraps silently. Arithmetic on values not proven small uses `checked_*`, `saturating_*` or `wrapping_*`, chosen on purpose: overflow wraps silently in release builds. No floats for money or other exact quantities.\n- **TYP-9 No unchecked access.** `get`, `first`, `last`, iterators, slice patterns, `split_first`, `chunks_exact` — not `v[i]` or `&s[a..b]`, unless the type proves the bounds (`[T; N]` with a constant index). No division or remainder by a value not proven non-zero.\n- **TYP-10 Compile time beats run time.** Generics and `impl Trait` over `dyn Any` and downcasts. Structs over `HashMap<String, Value>` bags. The borrow checker over `RefCell`. `const _: () = assert!(…);` for relationships between constants. `#[must_use]` on types and functions whose result must not be dropped. A panic in a `const` initialiser is a compile error, so `const N: NonZeroU32 = NonZeroU32::new(8).unwrap();` is fine.\n- **TYP-11 Stay proportionate.** When the type machinery would cost more clarity than the bug it prevents, step down one rung — to a validated newtype, never to \"unchecked\".\n\n```rust\n// BAD: meaningless values compile — running with an exit code, port 0, mode \"raed\".\nstruct Job {\n    running: bool,\n    exit_code: Option<i32>,\n    port: u16,\n    mode: String,\n}\n\n// GOOD: every value of these types is a legal state. (Doc comments left out of this sketch.)\nenum Job {\n    Queued,\n    Running { port: Port, mode: Mode },\n    Finished { exit: ExitStatus },\n}\n\nenum Mode {\n    Read,\n    Write,\n}\n\n/// TCP port; never 0.\n#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, serde::Deserialize)]\n#[serde(try_from = \"u16\")] // deserialization cannot bypass the check\npub struct Port(NonZeroU16);\n\nimpl TryFrom<u16> for Port {\n    type Error = PortError;\n\n    fn try_from(raw: u16) -> Result<Self, Self::Error> {\n        NonZeroU16::new(raw).map(Self).ok_or(PortError::Zero)\n    }\n}\n```\n\n## 7. Errors — `ERR`\n\n- **ERR-1 Nothing is ignored.** Every fallible outcome is (a) propagated with `?`, with context; or (b) recovered by a fallback that is specified behaviour and has a test; or (c) — only where it cannot be propagated: in `Drop`, or during cleanup while another error is already being returned — logged at `warn` or `error` with context, next to a comment saying why. \"Cannot happen\" and \"does not matter\" are not handling. If carrying on really is right, write the decision down: match the error, log it, comment why.\n- **ERR-2 All of these count as ignoring:**\n  - `let _ = f();`, `_ = f();`, `f().ok();`, an empty or catch-all `Err(_) => {}` arm;\n  - `if let Ok(x) = f()` or `while let Ok(x) = …` with the `Err` case unhandled;\n  - `.ok()`, `.unwrap_or(…)`, `.unwrap_or_default()`, `.unwrap_or_else(|_| …)` used to make a failure disappear rather than as a specified fallback;\n  - `filter_map(Result::ok)`, `.flatten()` or `.flat_map(…)` over `Result`s — failed items vanish; collect into `Result<Vec<_>, _>` or handle each error;\n  - `map_err(|_| …)` — the cause is thrown away;\n  - concurrency: a dropped `JoinHandle` (thread or task), an unchecked `JoinError`, an ignored `send` / `recv` error or timeout;\n  - I/O: `write` for `write_all`, `read` for `read_exact` (byte count ignored); a `BufWriter` dropped without `flush()?`; data that must survive a crash without `sync_all()?`; `Command::status()` / `output()` without checking `ExitStatus::success()`; a child process never waited for;\n  - lossy shortcuts — `as` casts, `from_utf8_lossy`, `to_string_lossy` — unless losing data is the specified behaviour;\n  - a `None` that means failure (lookup miss, `checked_*` overflow, `.parse().ok()`): convert it with `ok_or_else` and propagate;\n  - `mutex.lock().unwrap()`: map poisoning to an error, or recover on purpose with `PoisonError::into_inner` and a comment why the data is still consistent;\n  - unchecked FFI return codes and null pointers;\n  - logging the error and continuing as if the operation had succeeded.\n- **ERR-3 No panic paths in production code** — library or binary: no `unwrap()`, `expect()`, `panic!`, `todo!`, `unimplemented!`, `unreachable!`, and no `assert!` on anything derived from input. A panic means \"bug\", never \"bad input\" or \"I/O failed\". If failure is truly impossible, first make the types say so (§6). Only when they cannot: `expect(\"<the invariant>\")` under a local `#[expect(clippy::expect_used, reason = \"…\")]`. `debug_assert!` and `assert!` may state internal invariants; document them under `# Panics`.\n- **ERR-4 `thiserror` by default.** Every library crate and every module with domain logic returns its own typed error. `anyhow` is allowed only in the top layer of a binary (`main` and the glue that merely reports errors to a human), in tests, examples, benches and build or xtask scripts — never in a library's public API. Never `Box<dyn Error>`, `String`, `&str`, `()`, `bool` or `Option` to signal failure. No other error crates (`eyre`, `snafu`, …) unless the repository already uses them.\n- **ERR-5 Narrow error types.** One enum per module or operation, holding only the failures that can really happen there — not one crate-wide `Error`. A caller can match it exhaustively with no dead arms. Compose upwards with `#[source]` or `#[from]`.\n- **ERR-6 Variants say what failed, in domain terms, with the context needed to act:** path, id, key, offending value (never a secret). Not `Io(#[from] io::Error)` — which file, which operation? Use `#[from]` only where one source type has exactly one meaning; otherwise build the variant in `map_err(|source| …)`.\n- **ERR-7 Keep the cause chain.** Wrap the underlying error as the `source` (`#[source]`, `#[from]`, `#[error(transparent)]`). Never stringify it into a field, never drop it. Do not also print the source in the wrapper's message: reporters walk `source()` and would show it twice.\n- **ERR-8 Error type hygiene.** Messages are lowercase, concise, without a trailing full stop, and name the failed operation and value. Types are `Debug` + `Error` + `Send + Sync + 'static`, small (box large payloads), and `#[non_exhaustive]` when public and likely to grow. No third-party error type in a library's public API unless that dependency is deliberately part of the API.\n- **ERR-9 With `anyhow`:** `.context(…)` or `.with_context(|| …)` on every `?` that crosses a boundary (what was being done, with which input); print the whole chain (`{:#}` or `{:?}`); never `downcast` to decide what to do — an error you branch on needs a type.\n- **ERR-10 Handle each error once.** Return it (with context) or handle and log it — not both.\n- **ERR-11 Binaries** return `ExitCode` or `Result` from `main`: non-zero exit on failure, the full cause chain on stderr. No `std::process::exit` outside `main` — it skips destructors. Program output goes through an injected `impl Write`, not `println!`: testable, and a closed pipe becomes an `Err` instead of a panic.\n- **ERR-12 Fallible teardown gets a method.** `Drop` cannot return an error and must never panic. A type whose cleanup can fail (flush, commit, close) offers `fn close(self) -> Result<…>`; `Drop` is only a best-effort fallback that logs.\n- **ERR-13 Document failure.** Every `pub fn` that returns `Result` has `# Errors` (which variants, when). Anything that can panic has `# Panics`.\n\n```rust\n/// Why [`load_settings`] failed.\n#[derive(Debug, thiserror::Error)]\npub(crate) enum LoadSettingsError {\n    /// The settings file could not be read.\n    #[error(\"cannot read settings file {path:?}\")]\n    Read {\n        /// File that was being read.\n        path: PathBuf,\n        /// OS failure: kept as the cause, not repeated in the message.\n        source: std::io::Error,\n    },\n    /// The file is not valid settings JSON.\n    #[error(\"invalid settings in {path:?}\")]\n    Parse {\n        /// File that was being parsed.\n        path: PathBuf,\n        /// Parser's reason, with line and column.\n        source: serde_json::Error,\n    },\n}\n\n/// Loads the settings stored at `path`.\n///\n/// # Errors\n/// [`LoadSettingsError::Read`] if the file cannot be read,\n/// [`LoadSettingsError::Parse`] if it is not valid settings JSON.\npub(crate) fn load_settings(path: &Path) -> Result<Settings, LoadSettingsError> {\n    let text = std::fs::read_to_string(path).map_err(|source| LoadSettingsError::Read {\n        path: path.to_owned(),\n        source,\n    })?;\n    serde_json::from_str(&text).map_err(|source| LoadSettingsError::Parse {\n        path: path.to_owned(),\n        source,\n    })\n}\n\n#[cfg(test)]\nmod tests {\n    use super::*;\n\n    #[test]\n    fn load_settings_reports_the_path_when_the_file_is_missing() {\n        let dir = tempfile::tempdir().expect(\"temp dir\");\n        let missing = dir.path().join(\"settings.json\");\n\n        let err = load_settings(&missing).expect_err(\"the file does not exist\");\n\n        assert!(matches!(&err, LoadSettingsError::Read { path, .. } if *path == missing));\n    }\n}\n```\n\nCommon replacements:\n\n```rust\n// Fail on the first bad item. Design and idioms — `API`\n\n- **API-1 Borrow in, own out.** Parameters are `&str`, `&[T]`, `&Path` — not `&String`, `&Vec<T>`, `&PathBuf`. Take ownership (`String`, `impl Into<String>`) only when the function stores or consumes the value.\n- **API-2 No `clone()` to silence the borrow checker.** Restructure: narrower scopes, split borrows, `mem::take`, passing references. Clone when a second owner is really needed. Write `Arc::clone(&x)` for ref-counted handles so cheap clones are visible. `Cow` for values that are usually borrowed.\n- **API-3 Minimal visibility.** Private by default, `pub(crate)` for internal sharing, `pub` only for the intended API — every `pub` item is a compatibility promise. Fields are private unless the struct is plain data. Public enums and structs that will grow are `#[non_exhaustive]`.\n- **API-4 Standard traits.** `Debug` on every type (hand-written and redacting where it holds secrets). `Clone`, `PartialEq`/`Eq`, `Hash`, `Ord`, `Default` where they are meaningful and preserve the invariants. Conversions through `From`, `TryFrom`, `AsRef`, `FromStr`, `Display`: implement `From`, never `Into`; `From` is infallible and lossless, otherwise it is `TryFrom`. No `Deref` to fake inheritance.\n- **API-5 Naming follows the Rust API Guidelines.** `as_` (free borrow), `to_` (costly), `into_` (consuming). Getters without `get_`. `iter` / `iter_mut` / `into_iter`. `is_` / `has_` for `bool`. `try_` for fallible twins. `new` / `with_…` / `from_…` constructors. Acronyms as words (`HttpClient`). Names come from the domain: no `utils`, `helpers`, `common`, `misc` modules, no `Manager`, `Data`, `Info` filler.\n- **API-6 Small and flat.** A function does one thing. Early returns (`?`, `let … else`) instead of nesting. As a guide: at most 50 lines and 5 parameters; beyond that, group parameters into a struct or use a builder.\n- **API-7 Static before dynamic, concrete before abstract.** Concrete type, then generic or `impl Trait`, then `dyn Trait` only for real runtime heterogeneity. No trait, type parameter, feature flag or configuration option without a second real use.\n- **API-8 Iterators and pattern matching** over index loops and `is_some()` + `unwrap()`. A plain `for` loop still beats a chain nobody can read.\n- **API-9 No global mutable state.** No `static mut`. `LazyLock` / `OnceLock` only for true constants (a compiled regex, a lookup table). Configuration, clients, clocks and RNGs are passed in — which is also what makes the code testable.\n- **API-10 No magic values.** A named `const` with its unit and reason. No repeated literals.\n- **API-11 Current idioms, as far as the MSRV allows:** `let … else`, inline format arguments (`{x}`), `is_some_and`, `LazyLock`, native `async fn` in traits, `#[expect]`. Prefer std over the helper crates it has replaced (`lazy_static`, `once_cell`, `async-trait`) unless the repository's convention says otherwise.\n- **API-12 Clean modules.** Organised by domain, not by kind; one responsibility each. No glob imports, except `use super::*` in test modules and declared preludes. No dead code, commented-out code, `dbg!`, stray prints, or `TODO` / `FIXME` without an issue reference.\n\n## 9. Documentation — `DOC`\n\n- **DOC-1** Every public item has `///` docs: a one-sentence summary line, then `# Errors`, `# Panics`, `# Safety`, `# Examples` where they apply. Every crate and module opens with `//!` stating its purpose.\n- **DOC-2** Every `const`, `static`, type, enum variant and struct field — private ones too — has a doc comment saying what it is for: unit, valid range, invariant.\n- **DOC-3** Comments explain *why* (the decision, the invariant, the trade-off, a link to the spec or issue), not what the next line does. A comment that no longer matches the code is a bug.\n- **DOC-4** Doc examples compile and run as doctests and use `?`, not `unwrap`. Link items with intra-doc links (`` [`Type`] ``). When behaviour or public API changes, the README, CHANGELOG and docs change in the same PR.\n\n## 10. Unsafe — `UNS`\n\n- **UNS-1 Do not write `unsafe`.** New crates start with `#![forbid(unsafe_code)]`. `unsafe` is acceptable only when the task demands it and no safe alternative exists (std, or an audited crate) — and the PR must flag it for human review.\n- **UNS-2** Each `unsafe` block is minimal, holds one unsafe operation, and carries a `// SAFETY:` comment showing why every precondition holds. Every `unsafe fn` and `unsafe trait` documents `# Safety`.\n- **UNS-3 Sound by construction.** Unsafe code sits behind a safe API that no safe caller can misuse into undefined behaviour — enforced by types and private fields, not by documentation.\n- **UNS-4** Tests exercise the unsafe code, and run under Miri where the repository supports it.\n- **UNS-5 Never:** `static mut`; `transmute` where a safe conversion exists; `mem::zeroed` or `assume_init` on unproven data; `get_unchecked`, `unwrap_unchecked`, `unreachable_unchecked` without a benchmark proving the need; `unsafe impl Send` / `Sync` without a written proof; unwinding across FFI. In FFI: `#[repr(C)]`, every pointer and return code checked, ownership documented.\n\n## 11. Concurrency and async — `CON`\n\n- **CON-1 Never block the async runtime.** No `std::thread::sleep`, blocking file, network or process calls, long CPU work, or blocking lock and channel waits inside async code. Use the runtime's async APIs or `spawn_blocking`.\n- **CON-2 No lock guard or `RefCell` borrow across `.await`.** Critical sections are short: no I/O, callbacks or awaits while holding a lock. `std::sync::Mutex` for short synchronous sections; an async mutex only when the lock must span an `.await` — and question the design first.\n- **CON-3 Share by communicating.** Prefer moving ownership through channels, or one task that owns the state, over `Arc<Mutex<…>>`. Where locks are shared, their order is fixed and documented, and a check and the action that depends on it happen under the same lock.\n- **CON-4 Structured concurrency.** Every spawned task or thread has an owner that joins it and handles both its panic (`JoinError`) and its `Result`. No fire-and-forget. Long-lived work supports cancellation and graceful shutdown (`JoinSet`, `CancellationToken`, scoped threads).\n- **CON-5 Everything is bounded.** Bounded channels and queues. A concurrency limit (`Semaphore`, `buffer_unordered(n)`). A timeout on every external call. Retries capped, with backoff and jitter, and only for idempotent operations.\n- **CON-6 Cancellation safety.** Any `.await` may be the last thing a future does. Never leave an invariant broken across an await. In `select!` use cancel-safe operations, or pin the future outside the loop. Say so in the docs when a public async fn is not cancel-safe.\n- **CON-7** No `block_on` inside async code. Libraries do not create runtimes. A function is `async` only if it awaits.\n- **CON-8** No hand-rolled synchronisation primitives or lock-free structures unless the task requires them; then every atomic `Ordering` is justified in a comment and the code is tested with `loom`.\n\n## 12. Performance — `PERF`\n\n- **PERF-1 Correct and clear first.** Optimise only with a measurement. A PR that claims a speed-up shows the numbers before and after.\n- **PERF-2 Do not waste by default.** No needless `clone`, `to_owned`, `to_string` or `collect`. More than 2000 changed lines outside tests is a `[BLOCKER]` PR-1 with a proposed split, except for a purely mechanical PR (PR-6). A change between 1500 and 2000 explains the estimate under the lead's deviations; a missing explanation is MINOR PR-2.\n3. **Gate — LINT-2.** When the request supplies the harness gate at the reviewed commit, use its result, time and log path. Do not run the gate again. Run single tests when a finding needs them. If the record is absent or belongs to another commit, run `agent gate` as the request instructs. A red gate is a `[BLOCKER]`: name the failed step and the line of its log. An environmental failure is reported and the review continues. A passing second run after a failure is flaky (LINT-8); inspect the recorded failure. A failure in a test this PR adds or changes blocks; an unrelated existing failure disclosed with its message and location under *Flaky checks* is reported once as MINOR out of scope. If commands cannot run, say so and use the supplied record or CI result.\n4. **Test integrity — TDD-11, TDD-14.** Existing tests first:\n\n   ```sh\n   git diff <base>...HEAD -- '*.rs' | grep -nE '^-.*(#\\[(tokio::)?test|assert|should_panic)|^\\+.*#\\[ignore'\n   ```\n\n   An existing test that was removed, ignored or loosened is a `[BLOCKER]` unless the task explicitly changed the behaviour it specified. Either way it goes under NEEDS HUMAN.\n\n   Then the PR's own tests. The diff against `<base>` shows a test of this PR only as it is at the head: one that a RED commit added and a later commit loosened looks like any new test. So list the commits (`git log --reverse --format='%h %s' <base>..HEAD`) and compare each RED commit with the head:\n\n   ```sh\n   for red in $(git log --reverse --format=%h --grep='^RED:' <base>..HEAD); do\n       git diff \"$red\" HEAD -- '*.rs' |\n           grep -nE '^-.*(#\\[(tokio::)?test|assert|should_panic)|^\\+.*#\\[ignore' | sed \"s/^/$red: /\"\n   done\n   ```\n\n   A hit is a lead: read that test at the RED commit and at the head. A test edited, removed, ignored or loosened after its RED commit is a `[MAJOR]` (TDD-14), unless a `TEST-FIX:` commit made the change and the PR lists it under *Tests changed after RED*. Judge each listed one: accept a test that was wrong, reject one that was only in the way. A change of behaviour with no RED commit before its code and no `Test-First: not possible — <reason>` in its commit message is a `[MAJOR]` (TDD-1).\n5. **Sweep** the added lines (§3).\n6. **Tests first.** Read the tests as the specification: do they pin down every behaviour the task asks for, every error variant, the boundaries? Then prove they can fail: pick the riskiest new condition, break it for a moment (invert it, return early) and run the PR's tests — they must go red (TDD-2). Then prove one RED commit: take the riskiest, `git checkout --detach <red>`, run the test its message names and see it fail on the assertion the message quotes; go back with `git checkout -`. A RED commit that does not build, or whose test passes, is a `[BLOCKER]` (TDD-1). With `cargo-mutants` installed: `git diff <base>...HEAD > /tmp/pr.diff && cargo mutants --in-diff /tmp/pr.diff`; a surviving mutant in new behaviour is a `[MAJOR]`.\n7. **Implementation.** Read every changed file in full, and the callers of changed functions. Walk the checklist (§4).\n8. **Claims.** Judge every entry under *Deviations*: each `#[expect]`, new dependency, `unsafe` block and assumption. Accept or reject each one explicitly.\n9. **Report** in the format of §7.\n\n## 3. Mechanical sweep\n\nPrints the added lines that often hide a violation, as `file:line: code`:\n\n```sh\ngit diff -U0 <base>...HEAD -- '*.rs' | awk -v pat='[.](unwrap|expect)[(]|panic!|todo!|unimplemented!|unreachable!|let _ =|[.]ok[(][)]|unwrap_or|(if|while) let Ok[(]|Err[(]_|map_err[(][|]_|filter_map|flat_map|flatten[(]|#!?[[]allow|#[[]ignore|rustfmt::skip|unsafe|static mut| as [iuf][0-9]| as [iu]size|dbg!|print(ln)?!|Box<dyn|anyhow|process::exit|set_var|block_on|thread::sleep|[.]lock[(]|spawn[(]|TODO|FIXME' '\n  /^\\+\\+\\+ / { file = substr($2, 3); next }\n  /^@@/      { n = $3; sub(/^\\+/, \"\", n); sub(/,.*/, \"\", n); next }\n  /^\\+/      { if ($0 ~ pat) print file \":\" n \": \" substr($0, 2); n++ }'\n```\n\nA hit is a lead, not a finding. First establish whether it is production or test code (`tests/`, `benches/`, `examples/`, a `#[cfg(test)]` module), then judge it against the rule:\n\n- `unwrap(`, `expect(`, `panic!`, `todo!`, `unimplemented!`, `unreachable!` → ERR-3\n- `let _ =`, `.ok()`, `unwrap_or…`, `if let Ok(`, `while let Ok(`, `Err(_`, `map_err(|_|`, `filter_map`, `flat_map`, `flatten(` → ERR-2\n- `#[allow` → LINT-3; `rustfmt::skip` → LINT-1; `#[ignore` → TDD-11\n- ` as u8`, ` as usize`, … → TYP-8\n- `unsafe` → UNS-1, UNS-2; `static mut` → UNS-5, API-9\n- `Box<dyn`, `anyhow` → ERR-4\n- `dbg!`, `println!`, `eprintln!` → OBS-1, ERR-11; `process::exit` → ERR-11; `set_var` → SEC-8\n- `block_on` → CON-7; `thread::sleep` → CON-1; `.lock(` → CON-2; `spawn(` → CON-4\n- `TODO`, `FIXME` → API-12\n\nThe sweep cannot see unchecked indexing (`v[i]`), `bool` or `String` used as state, a lock held across `.await`, or a missing test. Those need reading. Where the repository's lint configuration is not strict, a harder clippy pass finds more — judge only the hits on lines the PR changed:\n\n```sh\ncargo clippy --workspace --all-targets --all-features -- -W clippy::unwrap_used -W clippy::expect_used \\\n    -W clippy::indexing_slicing -W clippy::let_underscore_must_use -W clippy::unused_result_ok \\\n    -W clippy::map_err_ignore -W clippy::allow_attributes\n```\n\n## 4. Checklist\n\n`B` = `[BLOCKER]`, `M` = `[MAJOR]`, `m` = `[MINOR]` (§6). Where a line carries several tags, the first applies unless the text says otherwise.\n\n**Correctness — `COR`** (plain defects; there is no developer rule number, cite `COR`)\n\n- `B` The code does not do what the task asks, or does something nobody asked for.\n- `B` Logic errors: a wrong condition, off-by-one, wrong order of operations, an unhandled edge case (empty, zero, max, duplicate, non-ASCII), a regression in existing behaviour.\n- `B` Resources: leaks, handles left open on error paths, half-finished state left behind when an operation fails midway.\n\n**Working discipline — `GEN`**\n\n- `m` **GEN-1** Re-implements something the repository already has.\n- `B` **GEN-3** A placeholder: stub body, hard-coded return value, \"implement later\", fake data path.\n- `M` **GEN-4** The implementation special-cases the inputs the tests use.\n- `M` **GEN-5** A hand-edited generated file, vendored code or lock file.\n- `m` **GEN-6** Narration comments (\"changed X to Y\").\n- `M` **GEN-7** The lead claims tests it did not run. The harness owns Size and Gate; compare its provenance to the reviewed commit.\n\n**Gate and lints — `LINT`**\n\n- `B` **LINT-1, LINT-2** The gate is red (step 3). `#[rustfmt::skip]` on anything but a hand-aligned table.\n- `M` **LINT-3** Any `#[allow]`. An `#[expect]` without a reason, on a wider scope than needed, with a reason that does not hold, or missing from the PR's *Deviations*.\n- `M` **LINT-4** Lint, format, toolchain or CI configuration changed in a feature PR. → NEEDS HUMAN\n- `M` **LINT-5** `#![deny(warnings)]` in source.\n- `M` **LINT-6** A language or std feature newer than the MSRV, or nightly-only.\n- `B` **LINT-8** (step 3) A test the PR adds or changes fails and then passes with nothing changed; the gate run a second time without the failure listed under `## Flaky checks`; a flaky test the developer met and did not report. A failure listed under `## Flaky checks`, in a test the diff does not touch, with its message and location, is `m`, out of scope, never a reason to request changes.\n\n**Tests — `TDD`** (TDD-1 shows in the commits, not in the diff: steps 4 and 6.)\n\n- `B` **TDD-1** (steps 4, 6) A RED commit that does not build, or whose test passes; a stub left at the head. `M` for a change of behaviour with no RED commit before its code and no `Test-First: not possible` reason.\n- `M` **TDD-2** A new behaviour, branch, error variant or bug fix without a test that fails when it is removed. Tests that cannot fail: no assertion, a tautology, asserting on a mock, repeating the implementation's logic.\n- `M` **TDD-3** A bug fix without a regression test.\n- `M` **TDD-4** A \"refactoring\" that changes behaviour or tests.\n- `m` **TDD-5** Tests coupled to private details that any refactoring would break.\n- `M` **TDD-6** An error variant, boundary or invalid input left untested — name which.\n- `M` **TDD-7** Errors asserted by message text, or only with `is_err()` / `is_ok()`; assertions too weak to pin the result.\n- `M` **TDD-8** Tests that are not deterministic or not isolated: real network, clock or sleep, unseeded randomness, fixed ports, shared global state, environment mutation, order dependence, files outside a temp directory.\n- `m` **TDD-9** Test names that do not say behaviour and condition; several unrelated checks in one test; copy-paste where a table would do.\n- `m` **TDD-10** A new inline `mod tests { }` where the module's tests belong in its `tests.rs`. The wrong kind of test: an integration test reaching into internals; a type-level guarantee without a compile-fail test; a parser or codec with example tests only, where a round-trip property is the obvious check.\n- `B` **TDD-11** (step 4) An existing test deleted, ignored, commented out or loosened. Skipped, empty or placeholder tests. → NEEDS HUMAN\n- `M` **TDD-12** Test-only paths in production code: `cfg!(test)` branches, test flags, visibility widened for tests.\n- `m` **TDD-13** A mock where the real implementation or an in-memory fake would do.\n- `M` **TDD-14** (step 4) A test of this PR edited, removed, ignored or loosened after its RED commit, without a listed `TEST-FIX` commit whose reason holds; a GREEN commit that changes tests.\n\n**Types — `TYP`** Ask of every new type and signature: *can I write a value or a call that compiles but is meaningless?* If a cheap type rules it out, it is a `[MAJOR]`.\n\n- `M` **TYP-1** Raw input travels inward unparsed; the same check repeated at several call sites instead of once in a constructor.\n- `M` **TYP-2** An invariant that can be bypassed: a `pub` field, a `Default` or `Deserialize` derive that skips validation, a setter, `DerefMut`.\n- `M` **TYP-3** A new signature whose same-typed arguments can be swapped by accident; ids, units or validated text as bare primitives.\n- `M` **TYP-4** A `bool` parameter; state, kind or mode as a string or integer; a sentinel value.\n- `M` **TYP-5** A struct with correlated `Option` / `bool` fields that should be an enum.\n- `M` **TYP-6** A `_ =>` arm on an enum defined in the workspace.\n- `m` **TYP-7** A protocol kept by convention (call order, \"remember to call close\") where ownership, typestate or a guard would enforce it.\n- `M` **TYP-8** A lossy `as` cast (narrowing, sign change, float to integer); unchecked arithmetic on values that come from outside; floats for money. `m` when the `as` cast is lossless (`u64::from(x)` is clearer).\n- `M` **TYP-9** `v[i]`, `&s[a..b]`, or division by an unproven value, in production code.\n- `m` **TYP-10** A runtime mechanism where the compile-time one is straightforward: `dyn Any`, a `HashMap<String, Value>` standing in for a struct, `RefCell` to dodge borrowing.\n- `m` **TYP-11** Type machinery clearly out of proportion to the risk.\n\n**Errors — `ERR`**\n\n- `M` **ERR-1, ERR-2** Any ignored outcome. Walk the list: a discarded result (`let _ =`, `.ok();`, an empty `Err` arm); a missing `Err` case; a failure masked by a default; failed items dropped from an iterator; the cause thrown away in `map_err(|_| …)`; an unobserved task, thread, channel or timeout result; a partial `write` / `read`, a missing `flush` / `sync_all`, an unchecked exit status, a child never waited for; a lossy shortcut; a `None` that means failure and is skipped; a poisoned lock unwrapped; an unchecked FFI result; log-and-continue. A fallback is acceptable only when it is specified behaviour *and* has a test.\n- `M` **ERR-3** A panic path in production code. `expect` is acceptable only under a local `#[expect(clippy::expect_used, reason = \"…\")]` — judge whether the reason holds.\n- `M` **ERR-4** `anyhow` outside a binary's top layer, tests, examples and scripts. `Box<dyn Error>`, `String`, `&str`, `()`, `bool` or `Option` signalling failure. A new error crate.\n- `M` **ERR-5** A catch-all crate-wide error enum; variants the function can never return.\n- `M` **ERR-6** A variant without the context needed to act (which file? which id?); a blanket `#[from]` that erases what was being done.\n- `M` **ERR-7** The cause stringified or dropped. `m` when the source is also printed in the message.\n- `m` **ERR-8** Message style; a public error enum that will grow without `#[non_exhaustive]`; an oversized error type; a third-party error type leaking through a library's public API.\n- `M` **ERR-9** `downcast` used to decide what to do. `m` when a `?` crosses a boundary without `.context(…)`.\n- `m` **ERR-10** The same error both logged and returned.\n- `M` **ERR-11** A binary that exits 0 on failure, hides the cause chain, or calls `process::exit` outside `main`. `m` for `println!` program output instead of an injected writer.\n- `M` **ERR-12** Fallible cleanup that exists only in `Drop`; a `Drop` that can panic.\n- `m` **ERR-13** Missing `# Errors` or `# Panics`.\n\n**Design — `API`**\n\n- `m` **API-1** `&String`, `&Vec<T>`, `&PathBuf` parameters; ownership taken without need.\n- `m` **API-2** `clone()` to appease the borrow checker; `.clone()` on an `Arc` / `Rc` instead of `Arc::clone(&x)`.\n- `m` **API-3** Wider visibility than needed; a growing public enum or struct without `#[non_exhaustive]`.\n- `m` **API-4** A type without `Debug`; `Into` implemented instead of `From`; a lossy `From`; `Deref` as inheritance.\n- `m` **API-5** Names against the Rust API Guidelines; `utils` / `helpers` dumping grounds.\n- `m` **API-6** A function that does several things; deep nesting; a long parameter list.\n- `m` **API-7** Speculative abstraction: a trait, type parameter, flag or option with a single user.\n- `m` **API-8** Index loops, or `is_some()` followed by `unwrap()`, where iterators or pattern matching fit.\n- `M` **API-9** `static mut`; new global mutable state.\n- `m` **API-10** Magic numbers or strings; repeated literals.\n- `m` **API-11** An outdated idiom or helper crate where std has the replacement.\n- `M` **API-12** Dead code, commented-out code, `dbg!`, a `TODO` / `FIXME` without an issue reference. `m` for glob imports and module organisation.\n\n**Documentation — `DOC`**\n\n- `M` **DOC-1** A public item without docs.\n- `m` **DOC-2** A `const`, `static`, type, variant or field without a doc comment.\n- `m` **DOC-3** Comments that restate the code. `M` when a comment has become false.\n- `m` **DOC-4** Doc examples using `unwrap`; README, CHANGELOG or docs not updated for a change in behaviour or public API.\n\n**Unsafe — `UNS`** Every new `unsafe` → NEEDS HUMAN.\n\n- `M` **UNS-1** `unsafe` the task does not require, or that has a safe alternative.\n- `M` **UNS-2** A block without a `// SAFETY:` proof, or holding more than one unsafe operation; an `unsafe fn` or `unsafe trait` without `# Safety`.\n- `M` **UNS-3** A safe API that a safe caller can misuse into undefined behaviour.\n- `M` **UNS-4** No test exercises the unsafe code. `m` when Miri is available and was not run.\n- `M` **UNS-5** A forbidden construct: `static mut`, avoidable `transmute`, `mem::zeroed` / `assume_init` on unproven data, unbenchmarked `*_unchecked`, unproven `unsafe impl Send` / `Sync`, unwinding across FFI, unchecked FFI pointers or return codes.\n\n**Concurrency and async — `CON`**\n\n- `M` **CON-1** A blocking call inside async code.\n- `M` **CON-2** A lock guard or `RefCell` borrow held across `.await`; I/O or a callback under a lock.\n- `M` **CON-3** Inconsistent lock order; a check and its dependent action under different lock acquisitions. `m` for `Arc<Mutex<…>>` where moving ownership would do.\n- `M` **CON-4** A task or thread that is never joined, or whose panic or `Result` nobody observes; long-lived work with no shutdown path.\n- `M` **CON-5** An unbounded channel, queue or spawn loop; an external call without a timeout; unbounded retries, or retries of a non-idempotent operation.\n- `M` **CON-6** State left inconsistent across an `.await`; an operation that is not cancel-safe inside `select!`.\n- `M` **CON-7** `block_on` inside async code; a runtime created in a library. `m` for an `async fn` that never awaits.\n- `M` **CON-8** A hand-rolled synchronisation primitive or lock-free structure without justification and `loom` tests.\n\n**Performance — `PERF`**\n\n- `m` **PERF-1** An optimisation without a measurement that costs clarity; a claimed speed-up without numbers.\n- `m` **PERF-2** Needless clones, allocations or collects; double lookups; unbuffered small I/O; a regex compiled per call.\n- `M` **PERF-3** Accidental O(n²) or an N+1 query on input that is not bounded; unbounded data loaded into memory.\n\n**Security — `SEC`** Changes to authentication, cryptography or secret handling → NEEDS HUMAN.\n\n- `M` **SEC-1** External input used without parsing or without bounds; allocation, loops or recursion driven by an unvalidated number.\n- `M` **SEC-2** A secret in source, tests, logs, error messages or `Debug` output; a comparison of secrets that is not constant-time.\n- `M` **SEC-3** SQL built by string concatenation; a shell string; a path joined from input without confinement.\n- `M` **SEC-4** Home-made cryptography; security values from an RNG that is not the OS CSPRNG; TLS verification disabled.\n- `M` **SEC-5** Check-then-act on the filesystem; predictable temporary file names.\n- `M` **SEC-6** Untrusted data deserialized without size limits, or into types that skip validation.\n- `M` **SEC-7** Internal details returned to remote callers; personal data in logs.\n- `M` **SEC-8** `std::env::set_var` / `remove_var` after startup.\n\n**Logging and output — `OBS`**\n\n- `M` **OBS-1** `println!`, `eprintln!` or `dbg!` in library code.\n- `m` **OBS-2** Interpolated strings instead of fields; wrong levels; `#[instrument]` capturing whole arguments.\n- `m` **OBS-3** The same error logged at several layers.\n\n**Dependencies — `DEP`** Every new dependency → NEEDS HUMAN.\n\n- `M` **DEP-1** A new dependency without justification, for trivial functionality, or unmaintained, obscure or licence-incompatible.\n- `M` **DEP-2** A `*`, git or path dependency; unrelated `Cargo.lock` churn. `m` for features not minimised, or a version outside `[workspace.dependencies]`.\n- `M` **DEP-3** `edition`, `rust-version`, profiles, toolchain or existing dependency versions changed outside the task. → NEEDS HUMAN\n- `M` **DEP-4** Cargo features that are not additive.\n- `M` **DEP-5** An unannounced breaking change to a public API. → NEEDS HUMAN\n\n**Pull request — `PR`**\n\n- `B` **PR-1, PR-2** Over the hard size limit of 2000 (step 2).\n- `m` **PR-2** Between 1500 and 2000 changed lines without a word under the lead's deviations on what the estimate missed.\n- `B` **PR-3** A part of a stack that does not build or pass on its own, or lacks the tests for what it adds.\n- `M` **PR-4** Mechanical and behavioural changes mixed in one PR.\n- `M` **PR-5** Unfinished functionality that users can reach.\n- `M` **PR-7** Unrelated changes: reformatted untouched code, drive-by refactoring, opportunistic fixes, unrequested features.\n- `M` **PR-8** Build artefacts, secrets or editor files committed. `m` for commit hygiene.\n- `M` **PR-9** A description that is missing sections or states something untrue.\n\n## 5. Not findings\n\nDo not report:\n\n- `unwrap`, `expect`, `panic!`, indexing or printing in test code (`#[cfg(test)]` modules, `tests/`, `benches/`); `anyhow` in tests, examples, build scripts and a binary's `main` and glue.\n- `expect(…)` under a local `#[expect(clippy::expect_used, reason = \"…\")]` whose reason holds; `unwrap()` in a `const` initialiser (it fails at compile time).\n- `.ok()`, `unwrap_or…` or `if let Ok` where the fallback is specified behaviour with a test.\n- `_ =>` on integers, strings, tuples and foreign `#[non_exhaustive]` enums.\n- `clone()` that creates a needed second owner (a value moved into a task, closure or struct); `Arc::clone`; clones in tests.\n- A `String` or `impl Into<String>` parameter when the function stores the value.\n- `std::sync::Mutex` in async code when the guard is not held across `.await`.\n- Plain arithmetic on small internal counters and on indices derived from `len()`.\n- Missing tests for pure refactoring, moves, docs or configuration; missing property tests or fuzzing where nothing calls for them.\n- In a stack of PRs: functionality not wired yet, an `#[expect(dead_code)]` that names a later part, work the plan assigns to a later part.\n- The size of the tests. Tests do not count toward the limit.\n- Tests added after a RED commit. An inline `mod tests { }` that was already there, also when the PR adds tests to it.\n- Anything in code the PR did not touch.\n- Formatting, naming case, import order — the gate decides those.\n- A missing optimisation without evidence that it matters.\n\n## 6. Severity and verdict\n\nEvery finding has exactly one of three severities. Write it in brackets, in capitals, and put nothing else in the\nbracket: the rule ID goes after it (`[MAJOR] ERR-3`), never in it.\n\n- `[BLOCKER]` — the logic does not work as it must, or there is a serious error: a red gate or build, a defect in\n  the code that the task or a test shows, a RED commit that does not build or whose test passes, an existing test\n  changed without the human, a size above 2000. It is fixed in the code and cannot be explained away.\n- `[MAJOR]` — a deviation from a specification (the task, the developer rules, `AGENTS.md`) that comes with no\n  explanation of why.\n- `[MINOR]` — everything else: a real improvement that does not block. At most 10, the most valuable first. The\n  limit applies to `[MINOR]` only.\n\nThe tags of §4 map to them once, here: `B` → `[BLOCKER]`, `M` → `[MAJOR]`, `m` → `[MINOR]`. They are defaults.\nRaise a finding one level only when it causes a concrete defect in this PR, and say which. A deviation the PR\nrecords under *Deviations* with a reason that holds, and that you accept, is not a finding: list it under ACCEPTED\nDEVIATIONS. If you cannot tell whether something is a violation, find out first: read, run. If it stays open and\nwould block, report it as a `[BLOCKER]` that asks for the evidence.\n\n**Verdict:** no `[BLOCKER]` and no `[MAJOR]` → `APPROVE`; otherwise `REQUEST_CHANGES`. `[MINOR]` findings never\nchange the verdict. A report that says `APPROVE` has no `[BLOCKER]` or `[MAJOR]` finding, and one that says\n`REQUEST_CHANGES` has at least one: the harness sends back a report that contradicts itself. If your harness or\ntask prescribes verdict keywords or a report layout, use those and keep the content.\n\n**NEEDS HUMAN** is independent of the verdict. List: new `unsafe`; existing tests changed or removed; a `TEST-FIX` you could not judge; lint, CI or toolchain configuration changes; new dependencies; changes to authentication, cryptography or secret handling; breaking public API changes; any deviation you were unsure about.\n\n## 7. Report format\n\nWhen the report quotes code, use a fenced block with the language of its source file (`rust`, `go`,\n`bash`, `toml`, `json`, and so on); use `text` for command output. Never leave a fence without a language.\n\n````text\nVERDICT: APPROVE | REQUEST_CHANGES\nSUMMARY: one or two sentences — what the PR does and why this verdict\nSIZE: 742 changed lines outside tests (planned for 1500, hard limit 2000)\nGATE: fmt ok, clippy ok, test ok, doc ok        (or: not run — <reason>)\n\nCRITERIA\nA1 met — `cargo test -p sync receiver_gone` passes; src/sync.rs:88\nA2 not met — the cap is 6, the task says \"at most 5\"; src/retry.rs:52\n\nFINDINGS\n1. [MAJOR] ERR-2 src/sync.rs:88 — `let _ = tx.send(evt)` drops the send error → return `SyncError::ReceiverGone`, or log it and stop the loop.\n   CHECK: `grep -n 'let _ =' src/sync.rs` finds nothing; `cargo test -p sync receiver_gone` passes\n\n```rust\nlet _ = tx.send(evt);\n```\n\n2. [BLOCKER] COR src/retry.rs:52 — the backoff cap is 6, the task says at most 5 → use 5.\n   CHECK: read src/retry.rs:52; `cargo test -p sync backoff_stops_at_the_cap` passes\n\n3. [MINOR] API-1 src/config.rs:17 — takes `&String` → `&str`.\n   CHECK: `grep -n '&String' src/config.rs` finds nothing\n\nACCEPTED DEVIATIONS\n- [ERR-3] src/re.rs:9 — `expect` on a literal regex, scoped `#[expect]`, covered by a test.\n- [TDD-14] src/retry/tests.rs:40 — `TEST-FIX` 3f2a91c: the test expected the cap one step too early; the task says \"at most 5\".\n\nNEEDS HUMAN\n- new dependency `foo` (DEP-1)\n\nOUT OF SCOPE\n- src/legacy.rs — `unwrap()` calls that were already there\n````\n\n- One finding, one numbered block: `N. [SEVERITY] RULE-ID file:line — problem → fix`, and under it, indented by\n  three spaces, `CHECK: …`.
