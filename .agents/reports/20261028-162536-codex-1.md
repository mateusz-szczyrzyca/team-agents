## Finding and resolution

Review #50 found `M3`: saving a complete manifest after the upload made its modification time newer than concurrent terminal metadata/activity writes. Later polls could skip those writes indefinitely.

The node captures a sibling reference inode before reading metadata or artifacts. It derives a conservative boundary from that inode's epoch second minus one, covering same-tick writes despite the strict `find -newer` comparison. This can cause an additional scan of very fresh files, while accepted hashes still avoid duplicate uploads.

All four manifest saves receive that boundary: clean legacy promotion, metadata-only acknowledgement, partial batch and final artifact batch. The JSON writer timestamps its temporary file before atomic replacement. Capture failures warn and leave the scan retryable; save/stamp failures preserve the previous manifest. Log-only terminal delivery keeps the existing manifest untouched. There is no new persisted field or reference-file leak on normal capture paths.

Minor `m1` remains deferred: retained logs have a record bound but no aggregate byte cap. This review pass does not change retention policy.

Independent inspection confirms neither committed RED test version shadows the harness `setup()`; the committed tests use the standard isolated harness. No cleanup or restoration of these live files was attempted after discovery, because it would require further changes to the installation. Operator inspection remains outstanding.
